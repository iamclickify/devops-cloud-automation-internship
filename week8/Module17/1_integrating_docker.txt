Pushing Docker Images to a Container Registry: Your Centralized Image Hub
Before we can automate anything, we need a place to store our built Docker images. Container registries serve as centralized repositories for your Docker images, much like Git repositories store your code. They allow you to version, manage, and share your containerized applications. For this lesson, we will focus on two popular options: Docker Hub and GitHub Container Registry (GHCR).

What is a Container Registry?
A container registry is a storage and distribution system for container images. When you build a Docker image, it's essentially a collection of layers that define your application's environment. Pushing this image to a registry makes it accessible to other machines, CI/CD pipelines, and deployment systems like Kubernetes. Registries are crucial for:

Image Versioning: Storing different versions of your application images.
Accessibility: Making images available for pulling by various services.
Collaboration: Sharing images among development teams.
Security: Often providing features for image scanning and access control.
Docker Hub: The Public Standard
Docker Hub is the default and most widely used public registry. It hosts a vast collection of official images (like Ubuntu, Alpine, Node.js) and community-contributed images. You can also create your own private or public repositories on Docker Hub to store your custom application images.

Key Features of Docker Hub:

Public & Private Repositories: Store images publicly or privately.
Automated Builds: Integrate with Git repositories (GitHub, Bitbucket) to automatically build images on code pushes.
Webhooks: Trigger actions in other services when an image is pushed.
Security Scanning: Basic vulnerability scanning for images.
GitHub Container Registry (GHCR): Integrated with GitHub Workflows
GitHub Container Registry (GHCR) is a newer offering that tightly integrates with GitHub Actions. If your code is hosted on GitHub, GHCR provides a seamless experience for building, storing, and deploying your container images directly within your GitHub workflows.

Key Features of GHCR:

Native GitHub Integration: Works seamlessly with GitHub Actions.
Fine-grained Permissions: Leverages GitHub's permission model.
Multiple Package Types: Supports Docker images, npm packages, Maven packages, and more.
Performance: Optimized for GitHub Actions.
Why Push to a Registry in CI/CD?
In a CI/CD pipeline, the build stage typically produces a Docker image. This image then needs to be stored in a registry so that subsequent stages (like testing, staging deployment, or production deployment) can access it. Without pushing to a registry:

Inconsistency: Each CI/CD runner would need to build the image independently, leading to potential inconsistencies.
Inefficiency: Rebuilding the same image multiple times is wasteful.
Deployment Challenges: Deployment tools like Kubernetes need a stable, accessible image to pull and run.
By pushing the built image to a registry, you create a single source of truth for your application's containerized artifact.

Practical Steps: Pushing to Docker Hub (Conceptual)
While we will automate this in the lab, the manual process involves:

Logging in: docker login
Tagging the image: docker tag my-app username/my-app:latest
Pushing the image: docker push username/my-app:latest
In our CI/CD workflow, these commands will be executed automatically by GitHub Actions.

Practical Steps: Pushing to GitHub Container Registry (Conceptual)
GHCR uses a slightly different tagging convention and authentication mechanism, which we'll cover in detail during the hands-on lab.

Key Takeaway: Container registries are essential for storing and managing your Docker images, acting as the bridge between your build process and your deployment environments. Docker Hub and GHCR are excellent choices, with GHCR offering tighter integration for GitHub-hosted projects.

Authenticating with Container Registries in CI/CD: Secure Access
Automating the process of pushing and pulling Docker images to and from registries requires your CI/CD system to authenticate securely. Hardcoding credentials directly into your workflow files is a major security risk. Instead, we must use secure methods to provide these credentials to the CI/CD runner.

The Need for Secure Authentication
When your GitHub Actions runner needs to push a Docker image to Docker Hub or GHCR, it needs to prove its identity. This is done through authentication. If this authentication is not handled securely, it can lead to:

Unauthorized Access: Malicious actors could gain access to your private image repositories.
Image Tampering: Attackers could potentially push malicious images to your repositories.
Account Compromise: Leaked credentials could compromise your entire Docker Hub or GitHub account.
Authentication Methods
The primary methods for authenticating CI/CD systems with container registries involve using tokens or secrets management.

1. Docker Hub Authentication
Docker Hub typically uses either a username and password or an access token for authentication.

Username and Password: While possible, this is generally discouraged for CI/CD due to security implications.
Access Tokens: Docker Hub allows you to generate access tokens. These tokens are more secure as they can be granted specific permissions and revoked easily.
How it works in CI/CD: You will store your Docker Hub username and your generated access token as GitHub Secrets. These secrets are then accessed within your GitHub Actions workflow to log in to Docker Hub.

2. GitHub Container Registry (GHCR) Authentication
GHCR leverages GitHub's built-in authentication mechanisms. The most common and recommended method is using a GitHub Personal Access Token (PAT) or, more securely, an OpenID Connect (OIDC) token.

Personal Access Token (PAT): You can generate a PAT with appropriate scopes (e.g., write:packages, read:packages) and store it as a GitHub Secret. The runner uses this PAT to authenticate with GHCR.
OpenID Connect (OIDC): This is the most secure and recommended approach. OIDC allows your GitHub Actions workflow to obtain short-lived, identity-bound credentials from GHCR without needing to store long-lived secrets like PATs. This significantly reduces the risk of credential leakage.
How it works with OIDC:

Configure your GitHub repository to trust your OIDC provider (GitHub Actions).
In your workflow, request an OIDC token for GHCR.
Use this token to log in to GHCR.
Why OIDC is preferred:

No Long-Lived Secrets: Eliminates the need to store sensitive PATs in GitHub Secrets.
Short-Lived Credentials: Tokens are temporary, limiting the window of exposure if compromised.
Auditable: Actions performed using OIDC tokens are tied to the specific workflow run.
Implementing Authentication in GitHub Actions
GitHub Actions provides a secure way to manage secrets. You can define secrets at the repository, organization, or environment level.

Steps to set up secrets:

Navigate to your GitHub repository's Settings.
Go to Secrets and variables > Actions.
Click New repository secret.
Add secrets for your registry credentials. For Docker Hub, you might create:
DOCKERHUB_USERNAME
DOCKERHUB_TOKEN
For GHCR (using PAT for simplicity in this explanation, though OIDC is better):

GHCR_USERNAME (often your GitHub username)
GHCR_TOKEN (a PAT with package scopes)
Accessing Secrets in Workflow Files:

Within your .github/workflows/main.yml file, you can access these secrets using the secrets context:

- name: Log in to Docker Hub
  uses: docker/login-action@v3
  with:
    username: ${{ secrets.DOCKERHUB_USERNAME }}
    password: ${{ secrets.DOCKERHUB_TOKEN }}

- name: Log in to GitHub Container Registry
  uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }} # Or a PAT if not using OIDC
Note on GITHUB_TOKEN: GitHub automatically provides a GITHUB_TOKEN for each workflow run. This token has limited permissions but can be used to authenticate with GHCR if your repository is public or if you grant it the necessary scopes. For private repositories or more robust control, a PAT or OIDC is recommended.

Best Practices for Authentication
Use Access Tokens/PATs: Never use your actual account password.
Grant Least Privilege: Ensure tokens have only the necessary permissions (e.g., read/write for packages, not full account access).
Use OIDC for GHCR: Prioritize OIDC for enhanced security.
Rotate Secrets Regularly: Especially if using PATs.
Store Secrets in GitHub Secrets: Never commit credentials directly into your code.
Use Environment-Specific Secrets: For different deployment stages (dev, staging, prod).
Secure authentication is the bedrock of a trustworthy CI/CD pipeline. By properly managing your registry credentials, you protect your containerized applications and your infrastructure.

Automating Docker Image Builds on Code Commits: The CI Trigger
The core of Continuous Integration (CI) is automating the build process whenever code changes are committed. For Dockerized applications, this means automatically building a new Docker image whenever a developer pushes code to the repository. This ensures that your container images are always up-to-date with the latest codebase.

The CI Trigger: Code Commits
In a CI/CD pipeline, the trigger for initiating a build is typically an event in your version control system. For GitHub Actions, this is most commonly a push event to a specific branch (like main or develop) or a pull_request event.

Why automate builds on commits?

Fast Feedback: Developers receive immediate feedback on whether their changes integrate correctly and can be containerized without errors.
Consistency: Every commit triggers the same build process, ensuring consistency.
Reduced Manual Effort: Eliminates the tedious and error-prone task of manually building images.
Early Bug Detection: Issues related to building the Docker image or dependencies are caught early in the development cycle.
Configuring GitHub Actions for Automated Builds
We use a YAML file (typically located at .github/workflows/main.yml) to define our GitHub Actions workflows. To automate Docker builds, we need to specify the trigger and then define the steps for building the image.

Example Workflow Snippet (Trigger):

name: CI/CD Pipeline

on:
  push:
    branches: [ main ] # Trigger on push to the main branch
  pull_request:
    branches: [ main ] # Also trigger on pull requests to main
This configuration tells GitHub Actions to run the workflow whenever code is pushed to the main branch or when a pull request targeting the main branch is opened or updated.

The Docker Build Step
Within the workflow, we'll use the docker/build-push-action, a popular and efficient action for building and optionally pushing Docker images.

Example Workflow Snippet (Build Step):

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v4

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    - name: Log in to Docker Hub
      uses: docker/login-action@v3
      with:
        username: ${{ secrets.DOCKERHUB_USERNAME }}
        password: ${{ secrets.DOCKERHUB_TOKEN }}

    - name: Build and push Docker image
      uses: docker/build-push-action@v5
      with:
        context: .
        file: ./Dockerfile
        push: true # Set to true to push the image after building
        tags: ${{ secrets.DOCKERHUB_USERNAME }}/my-app:latest # Example tag
Explanation of the Build Step:

context: .: Specifies the build context (the directory containing the Dockerfile and source code).
file: ./Dockerfile: Points to the Dockerfile to use for the build.
push: true: This crucial parameter tells the action to push the image to the registry after a successful build.
tags: ...: Defines the tags for the image. We'll discuss tagging strategies in more detail in the next section.
Integrating with Your Application
For this to work, you need:

A Dockerfile in the root of your project that defines how to build your application's image.
Your application code committed to a GitHub repository.
The necessary secrets (DOCKERHUB_USERNAME, DOCKERHUB_TOKEN) configured in your GitHub repository settings.
Real-World Scenario: A Web Application
Imagine a team developing a Node.js web application. Every time a developer pushes a new feature or bug fix to the main branch:

GitHub Actions automatically detects the push.
The workflow checks out the latest code.
Docker Buildx is set up.
The runner logs into Docker Hub using stored secrets.
The docker/build-push-action builds the Docker image using the project's Dockerfile.
The newly built image is tagged (e.g., with username/my-web-app:latest) and pushed to Docker Hub.
This image is now ready to be deployed to a staging or production environment.
This automated process ensures that your containerized application is always synchronized with your codebase, enabling rapid iteration and deployment.

Tagging Docker Images with Commit SHAs and Version Numbers: Version Control for Images
Effective image tagging is crucial for managing your Docker image lifecycle within a CI/CD pipeline. Simply using a latest tag is often insufficient for production environments, as it can lead to ambiguity and make rollbacks difficult. We need a strategy that provides traceability and allows us to pinpoint specific versions of our application.

Why Tagging Matters in CI/CD
Docker images, like code, need version control. Tags act as human-readable labels pointing to specific image digests (unique identifiers). In a CI/CD context, proper tagging enables:

Traceability: Linking a deployed container back to the exact commit or version of the code it was built from.
Rollbacks: Easily deploying a previous, known-good version of an image if issues arise.
Reproducibility: Ensuring that you can reliably rebuild or deploy a specific version of your application.
Deployment Strategies: Facilitating advanced deployment patterns like blue-green or canary deployments.
Common Tagging Strategies
Several strategies can be employed, often in combination:

1. Using the Git Commit SHA
This is a highly recommended practice for CI/CD. Each commit in Git has a unique SHA (Secure Hash Algorithm) identifier. Using this SHA as a Docker image tag provides a direct link between the code and the image.

Benefits:

Uniqueness: Every commit gets a unique tag.
Traceability: Directly maps an image to its source code commit.
Reproducibility: You can always find the exact code that built a specific image.
Implementation in GitHub Actions: GitHub Actions provides access to the commit SHA through the github.sha context variable.

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    # ... checkout and login steps ...

    - name: Build and push Docker image with commit SHA tag
      uses: docker/build-push-action@v5
      with:
        context: .
        file: ./Dockerfile
        push: true
        tags: |
          ${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.sha }}
          ${{ secrets.DOCKERHUB_USERNAME }}/my-app:latest # Optionally also tag as latest
In this example, the image will be tagged with the full commit SHA (e.g., username/my-app:a1b2c3d4e5f6...). You can also choose to tag it with a shortened SHA or include the latest tag for convenience, though be mindful of overwriting.

2. Using Git Tags (Semantic Versioning)
When you release a stable version of your application, you typically tag your Git repository using semantic versioning (e.g., v1.0.0, v1.1.0). These Git tags are excellent candidates for Docker image tags.

Benefits:

Clear Versioning: Aligns Docker image versions with application releases.
Human-Readable: Easier to understand than commit SHAs for release management.
Implementation in GitHub Actions: You can trigger workflows specifically on Git tags or access the tag name.

name: CI/CD Pipeline

on:
  push:
    tags: [ 'v*.*.*' ] # Trigger only on tags starting with 'v'

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    # ... checkout and login steps ...

    - name: Build and push Docker image with Git tag
      uses: docker/build-push-action@v5
      with:
        context: .
        file: ./Dockerfile
        push: true
        tags: |
          ${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.ref_name }}
Here, ${{ github.ref_name }} will resolve to the Git tag name (e.g., v1.2.3). This is ideal for release builds.

3. Combining Strategies
A robust strategy often combines both commit SHAs and Git tags:

On every push to main: Tag the image with the commit SHA and potentially latest.
On a Git tag push (e.g., v1.2.3): Tag the image with the Git tag (v1.2.3) and the commit SHA that the tag points to.
This provides both precise traceability (SHA) and clear release versioning (Git tag).

Prerequisites:

Steps:

Modify the Trigger: Ensure your workflow triggers on tag pushes.

This ensures the workflow only runs when you explicitly create a Git tag.

Best Practices for Tagging
Never rely solely on latest for production.
Always include the Git commit SHA for unambiguous traceability.
Use semantic versioning for release tags.
Consider immutable tags (like commit SHAs) for production deployments.
Document your tagging strategy clearly.
By implementing a consistent and informative tagging strategy, you gain significant control and visibility over your containerized application's lifecycle.

Security Scanning of Docker Images within the Pipeline: Proactive Vulnerability Management
Building secure software is paramount, and this extends to the container images themselves. Docker images are composed of base operating system layers and application dependencies, all of which can contain vulnerabilities. Integrating security scanning directly into your CI/CD pipeline ensures that potential security risks are identified and addressed early, before they reach production.

Why Scan Docker Images in CI/CD?
Scanning images within the pipeline provides several critical benefits:

Early Detection: Vulnerabilities are found during the build process, when they are easiest and cheapest to fix.
Shift-Left Security: Security becomes an integral part of the development workflow, not an afterthought.
Reduced Risk: Prevents vulnerable images from being deployed to production environments.
Compliance: Helps meet security compliance requirements.
Automated Enforcement: The pipeline can be configured to fail if critical vulnerabilities are detected.
Common Vulnerability Scanning Tools
Several excellent open-source and commercial tools can be integrated into CI/CD pipelines:

1. Trivy (Aqua Security)
Trivy is a popular, versatile, and easy-to-use open-source scanner. It can scan container images, filesystems, and Git repositories for vulnerabilities, misconfigurations, and secrets.

Key Features:

Comprehensive Scans: Detects OS package vulnerabilities (Alpine, RHEL, CentOS, Debian, Ubuntu, etc.) and application dependency vulnerabilities (npm, yarn, pip, Maven, Gradle, etc.).
Misconfiguration Detection: Checks for common security misconfigurations in container images.
Secret Detection: Identifies hardcoded secrets within images.
Fast and Simple: Easy to install and run.
Integration: Designed for CI/CD integration.
2. Clair (Quay.io)
Clair is an open-source static analysis tool for the vulnerability of Docker images. It analyzes image layers and compares them against vulnerability databases.

3. Anchore Engine / Grype
Anchore provides tools for container security analysis. Grype is their open-source scanner that integrates well into CI/CD pipelines.

4. Commercial Tools
Many commercial solutions offer advanced features, including deeper scanning, policy enforcement, and integration with cloud platforms (e.g., Snyk, Twistlock, Aqua Security Platform).

Integrating Trivy into GitHub Actions
Trivy is an excellent choice for integration due to its simplicity and effectiveness. We can use a dedicated GitHub Action for Trivy or run the Trivy binary directly.

Using the Trivy GitHub Action:

A common pattern is to scan the image immediately after it has been built and pushed.

jobs:
  build_and_scan:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v4

    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    - name: Log in to Docker Hub
      uses: docker/login-action@v3
      with:
        username: ${{ secrets.DOCKERHUB_USERNAME }}
        password: ${{ secrets.DOCKERHUB_TOKEN }}

    - name: Build and push Docker image
      id: docker_build # Give this step an ID to reference its outputs
      uses: docker/build-push-action@v5
      with:
        context: .
        file: ./Dockerfile
        push: true
        tags: |
          ${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.sha }}
          ${{ secrets.DOCKERHUB_USERNAME }}/my-app:latest

    - name: Scan Docker image vulnerabilities with Trivy
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: '${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.sha }}' # Scan the image we just pushed
        format: 'table'
        exit-code: '1' # Fail the build if vulnerabilities are found (adjust severity as needed)
        ignore-unfixed: true # Ignore vulnerabilities that have no fix available
        vuln-type: 'os,app'
        severity: 'CRITICAL,HIGH' # Only fail on CRITICAL or HIGH severity vulnerabilities
Explanation of the Trivy Step:

image-ref: Specifies the Docker image to scan. We use the SHA tag for precise scanning.
format: 'table': Outputs the results in a human-readable table format.
exit-code: '1': This is crucial for CI/CD. If Trivy finds vulnerabilities matching the specified criteria, it will exit with a non-zero status code, causing the GitHub Actions job to fail.
ignore-unfixed: true: Useful for managing vulnerabilities that do not yet have a patch available.
vuln-type: 'os,app': Scans for both operating system package vulnerabilities and application dependency vulnerabilities.
severity: 'CRITICAL,HIGH': Configures Trivy to only fail the build if vulnerabilities of CRITICAL or HIGH severity are found. You can adjust this based on your organization's risk tolerance.
Lab: Integrate a Security Scan Step
Let's add the Trivy scan to our existing workflow.

Prerequisites:

A GitHub repository with a Dockerfile and a working CI workflow that builds and pushes an image.
Docker Hub credentials set as secrets (DOCKERHUB_USERNAME, DOCKERHUB_TOKEN).
Steps:

Add the Trivy Action: Append the Trivy scanning step to your .github/workflows/main.yml file, after the Docker build and push step.
# ... (previous steps for checkout, login, build/push) ...

    - name: Scan Docker image vulnerabilities with Trivy
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: '${{ secrets.DOCKERHUB_USERNAME }}/my-app:${{ github.sha }}'
        format: 'table'
        exit-code: '1' # Fail build on critical/high vulnerabilities
        ignore-unfixed: true
        vuln-type: 'os,app'
        severity: 'CRITICAL,HIGH'
2. Test the Scan:

Commit the updated workflow file.
Trigger a build (e.g., by pushing to main or creating a tag).
Observe the GitHub Actions run. If Trivy detects CRITICAL or HIGH severity vulnerabilities in your image, the job will fail at the scanning step.
Troubleshooting:

False Positives: Sometimes scanners report vulnerabilities that are not exploitable in your specific context. Trivy's ignore-unfixed and severity controls help manage this. For more advanced cases, consider vulnerability suppression features.
Performance: Scanning can add time to your pipeline. Optimize your Dockerfile (e.g., multi-stage builds, minimal base images) to reduce image size and scan times.
Custom Rules: For specific compliance needs, you might need to explore more advanced tools or custom scanning logic.
By integrating security scanning, you transform your CI/CD pipeline from a simple build and deploy mechanism into a robust security gate, ensuring that only secure container images proceed through your delivery process.

Best Practices for CI/CD Docker Image Management
Effectively managing Docker images within your CI/CD pipeline is crucial for maintaining security, reliability, and efficiency. Adopting best practices ensures that your containerization strategy scales with your application and team.

1. Use Minimal Base Images
Start with the smallest possible base image that meets your application's needs. Smaller images have fewer potential vulnerabilities, reduce build times, and consume less storage space.

Alpine Linux: A popular choice for its minimal footprint.
Distroless Images: Images that contain only your application and its runtime dependencies, with no shell or package manager.
Official Images: Use official images from trusted sources (e.g., official Node.js, Python images) as they are generally well-maintained.
Example Dockerfile Snippet:

# Instead of FROM ubuntu:latest
FROM alpine:latest

# Or for Node.js
FROM node:18-alpine
2. Multi-Stage Builds
Multi-stage builds allow you to use one container image for building your application and a separate, minimal image for running it. This significantly reduces the final image size by excluding build tools, development dependencies, and intermediate artifacts.

Example Dockerfile Snippet:

# Stage 1: Build the application
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./ 
RUN npm install
COPY . .
RUN npm run build

# Stage 2: Run the application
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist # Copy only the build artifacts
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package.json . 
CMD ["node", "dist/server.js"]
3. Leverage Build Caching
Docker builds layer by layer. By structuring your Dockerfile correctly, you can leverage Docker's build cache. Frequently changing instructions (like copying source code) should be placed later in the Dockerfile, while less frequently changing instructions (like installing dependencies) should be placed earlier.

Example: Install dependencies before copying application code.

FROM node:18-alpine
WORKDIR /app

# Install dependencies first - this layer is cached if package.json does not change
COPY package*.json ./ 
RUN npm install

# Copy application code - this layer changes more often
COPY . .

CMD ["npm", "start"]
4. Scan Images for Vulnerabilities (As Covered)
Regularly scan your images for OS and application dependency vulnerabilities using tools like Trivy. Integrate these scans into your CI pipeline to fail builds on critical issues.

5. Implement Robust Tagging Strategies (As Covered)
Use commit SHAs and Git tags for clear versioning and traceability. Avoid relying solely on the latest tag for production deployments.

6. Store Images in a Reliable Registry
Use a reputable container registry like Docker Hub or GitHub Container Registry (GHCR). For private applications, ensure you are using private repositories and managing access securely.

7. Scan for Secrets
Ensure your build process does not accidentally embed secrets (API keys, passwords) into your images. Tools like Trivy can help detect these.

8. Automate Image Cleanup
Over time, your container registry can accumulate old, unused images. Implement a strategy for cleaning up old images to save storage costs and reduce clutter. This can be done via scripts or registry-specific lifecycle policies.

9. Use Image Signing and Verification
For enhanced security, consider signing your Docker images using tools like Notary or Docker Content Trust. This allows consumers of your images to verify their authenticity and integrity.

10. Define Clear Image Promotion Strategies
Establish a clear process for how images move through different environments (e.g., from development to staging to production). This often involves using specific tags for each environment and potentially implementing manual approval gates.

11. Optimize Dockerfile Instructions
Combine related RUN commands where logical to reduce the number of layers.
Use COPY instead of ADD unless you specifically need ADD's features (like URL fetching or auto-extraction).
Clean up temporary files created during builds within the same RUN command to keep layers small.
12. Consider Security Contexts and Non-Root Users
Run your application within the container as a non-root user whenever possible. This is a fundamental security principle that limits the potential impact if the container is compromised.

Example Dockerfile Snippet:

# ... (previous steps) ...

# Create a non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Switch to the non-root user
USER appuser

# ... (rest of your Dockerfile) ...
By consistently applying these best practices, you build a more robust, secure, and efficient CI/CD pipeline for your containerized applications.

Practical Application: Building and Pushing Your First CI/CD Docker Image

Now, let's put everything we've learned into practice. This lab will guide you through setting up a GitHub Actions workflow to automatically build a Docker image from your application code and push it to a container registry.

Lab Objective
To modify a GitHub Actions workflow to:

Checkout your application code.
Build a Docker image using a provided Dockerfile.
Push the built image to Docker Hub.
Tag the image with the Git commit SHA.
Integrate a security scan using Trivy.
Prerequisites
A GitHub account (free tier is sufficient).
A GitHub repository containing a simple application (e.g., a basic Node.js web server, a Python Flask app, or even a static HTML site).
A Dockerfile in the root of your repository that can build your application.
A Docker Hub account.
Secrets configured in your GitHub repository:
DOCKERHUB_USERNAME: Your Docker Hub username.
DOCKERHUB_TOKEN: A Docker Hub access token (generate one from your Docker Hub account settings under Security > Access Tokens). Ensure it has read/write permissions.
Docker Desktop installed locally (optional, but helpful for testing your Dockerfile).

Step 2: Create the GitHub Actions Workflow File
In the root of your repository, create a directory named .github, and inside it, create another directory named workflows. Inside workflows, create a file named docker-build-ci.yml.

Paste the following content into .github/workflows/docker-build-ci.yml:

name: Docker Build and Push CI

# Trigger the workflow on push events to the main branch
# and on pull requests targeting the main branch.
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build_and_push:
    runs-on: ubuntu-latest

    steps:
    # 1. Checkout code
    - name: Checkout code
      uses: actions/checkout@v4

    # 2. Set up Docker Buildx
    # Buildx is a Docker CLI plugin that extends the 'docker build' command
    # with the full features of Moby BuildKit. It enables features like 
    # multi-platform builds and better caching.
    - name: Set up Docker Buildx
      uses: docker/setup-buildx-action@v3

    # 3. Log in to Docker Hub
    # This step uses the docker/login-action to authenticate with Docker Hub.
    # It retrieves your username and access token from GitHub Secrets.
    - name: Log in to Docker Hub
      uses: docker/login-action@v3
      with:
        username: ${{ secrets.DOCKERHUB_USERNAME }}
        password: ${{ secrets.DOCKERHUB_TOKEN }}

    # 4. Build and push Docker image
    # This step uses the docker/build-push-action to build the Docker image
    # and push it to Docker Hub. It tags the image with the Git commit SHA.
    - name: Build and push Docker image
      id: docker_build # Assign an ID to reference this step's outputs if needed
      uses: docker/build-push-action@v5
      with:
        context: .
        file: ./Dockerfile
        push: true
        tags: |
          ${{ secrets.DOCKERHUB_USERNAME }}/simple-docker-app:${{ github.sha }}
          ${{ secrets.DOCKERHUB_USERNAME }}/simple-docker-app:latest # Also tag as latest for convenience

    # 5. Scan Docker image vulnerabilities with Trivy
    # This step uses the aquasecurity/trivy-action to scan the newly pushed image.
    # The job will fail if CRITICAL or HIGH severity vulnerabilities are found.
    - name: Scan Docker image vulnerabilities with Trivy
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: '${{ secrets.DOCKERHUB_USERNAME }}/simple-docker-app:${{ github.sha }}'
        format: 'table'
        exit-code: '1' # Fail the build if vulnerabilities are found
        ignore-unfixed: true # Ignore vulnerabilities that have no fix available
        vuln-type: 'os,app'
        severity: 'CRITICAL,HIGH'
Step 3: Configure GitHub Secrets
Go to your GitHub repository's Settings > Secrets and variables > Actions.

Click New repository secret and add the following:

Name: DOCKERHUB_USERNAME
Value: Your Docker Hub username
Name: DOCKERHUB_TOKEN
Value: Your Docker Hub access token
Make sure you have generated an access token from Docker Hub and granted it appropriate permissions (e.g., Read, Write).

Step 4: Test the Workflow
Commit the .github/workflows/docker-build-ci.yml file to your repository.

Push a change to your main branch:

git add .
git commit -m "Add CI workflow for Docker build"
git push origin main
Navigate to the Actions tab in your GitHub repository. You should see your workflow running.

Observe the steps:

Checkout code: Fetches your repository's content.
Set up Docker Buildx: Prepares the Docker build environment.
Log in to Docker Hub: Authenticates using your secrets.
Build and push Docker image: Builds the image and pushes it to your Docker Hub repository. Check your Docker Hub account to see the new image tagged with your commit SHA and latest.
Scan Docker image vulnerabilities with Trivy: Scans the pushed image. If any CRITICAL or HIGH severity vulnerabilities are found, this step will fail, and the entire workflow run will be marked as failed.

Troubleshooting Common Issues
Authentication Failed: Double-check your DOCKERHUB_USERNAME and DOCKERHUB_TOKEN secrets. Ensure the token has the necessary permissions.
Dockerfile Not Found: Verify that your Dockerfile is in the root directory and the path in the workflow is correct (./Dockerfile).
Build Errors: Examine the logs for the "Build and push Docker image" step. Errors here usually indicate issues within your Dockerfile or application code.
Scan Failures: If the Trivy scan fails, review the logs to understand the detected vulnerabilities. You might need to update dependencies or base images.
Image Not Pushed: Ensure push: true is set in the docker/build-push-action step.
