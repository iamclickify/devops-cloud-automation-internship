Understanding Kubernetes Deployment Strategies in CI/CD
Before we dive into the practical implementation, it's essential to grasp the fundamental concepts of how CI/CD pipelines interact with Kubernetes for application deployments. At its core, a CI/CD pipeline automates the process of taking code changes from a repository, building them into deployable artifacts (like Docker images), and then deploying those artifacts to a target environment. When that target environment is Kubernetes, the pipeline needs specific tools and configurations to communicate with the cluster and manage application resources.

What are Kubernetes Deployments?

In Kubernetes, a Deployment is a Kubernetes API object that manages a set of identical Pods. It provides declarative updates for Pods and ReplicaSets. A Deployment describes the desired state for your application, including the container image to use, the number of replicas, and update strategies. The Kubernetes control plane then works to ensure the actual state of your cluster matches this desired state.

Why is Automating Kubernetes Deployments Crucial?

Manual deployments to Kubernetes are prone to human error, time-consuming, and difficult to scale. Automating these deployments via CI/CD offers numerous benefits:

Speed and Efficiency: Rapidly deploy new features and bug fixes.
Consistency and Reliability: Eliminate manual errors and ensure deployments are repeatable.
Reduced Downtime: Implement sophisticated rollout strategies to minimize service interruptions.
Scalability: Easily manage deployments across multiple environments and clusters.
Traceability: Every deployment is linked to a specific commit, providing an audit trail.
Developer Productivity: Developers can focus on writing code, not on deployment mechanics.
Connecting CI/CD to Kubernetes

A CI/CD pipeline orchestrates Kubernetes deployments by executing commands or API calls that interact with the Kubernetes API server. This typically involves using tools like kubectl or package managers like Helm. The pipeline needs to be configured with the necessary credentials and context to authenticate with the target Kubernetes cluster.

Key Components of a Kubernetes Deployment Pipeline:

Source Code Repository: Where your application code resides (e.g., GitHub).
CI Server: Orchestrates the pipeline (e.g., GitHub Actions).
Build Environment: Compiles code, builds Docker images.
Container Registry: Stores Docker images (e.g., Docker Hub, GitHub Container Registry).
Kubernetes Cluster: The target environment for deployment.
Deployment Tools: kubectl, Helm, or GitOps tools.
This lesson will focus on the critical link between the CI server and the Kubernetes cluster, detailing how to use kubectl and Helm to manage your application deployments.

Authenticating with Kubernetes Clusters from CI/CD
Securely authenticating your CI/CD pipeline with your Kubernetes cluster is the foundational step for any automated deployment. Without proper authentication, your pipeline will lack the necessary permissions to interact with the Kubernetes API server, preventing any deployment actions.

What is Kubernetes Authentication?

Kubernetes uses a pluggable authentication system. When a user or service account makes a request to the Kubernetes API server, the API server authenticates the request. This process verifies the identity of the requester. For CI/CD pipelines, this typically means authenticating as a specific service account or using a user credential that has been granted appropriate permissions.

Why is Secure Authentication Critical?

Security: Unauthorized access to your Kubernetes cluster can lead to data breaches, service disruptions, and compromise of your entire infrastructure. CI/CD pipelines often run with elevated privileges, making their authentication credentials a high-value target.

Least Privilege Principle: It is crucial to grant your CI/CD pipeline only the permissions it absolutely needs to perform its tasks. Overly permissive credentials can be exploited.

Reproducibility: Secure and consistent authentication ensures that your deployments are repeatable and predictable.

Methods for Kubernetes Authentication in CI/CD:

There are several common methods to authenticate CI/CD pipelines with Kubernetes:

Service Account Tokens: This is the most common and recommended method for CI/CD. You create a dedicated Kubernetes ServiceAccount within your cluster and grant it specific RBAC (Role-Based Access Control) permissions. The CI/CD pipeline then uses the token associated with this ServiceAccount to authenticate.
kubeconfig Files: A kubeconfig file contains cluster connection information, including authentication credentials. You can securely store this file as a secret in your CI/CD system and use it to configure kubectl or Helm.
Cloud Provider IAM Roles (e.g., AWS IAM Roles for Service Accounts - IRSA): If your Kubernetes cluster is hosted on a cloud provider, you can leverage their Identity and Access Management (IAM) services. For example, AWS IRSA allows pods (and thus, CI/CD runners that might run as pods) to assume IAM roles, granting them permissions to interact with cloud resources, including the Kubernetes API.
Implementing Service Account Authentication with GitHub Actions (Recommended Approach)

This approach involves creating a Service Account in your Kubernetes cluster and then securely passing its token to your GitHub Actions workflow.

Step 1: Create a Service Account and Role/ClusterRole in Kubernetes

First, define a ServiceAccount, a Role (for namespace-specific permissions) or ClusterRole (for cluster-wide permissions), and a RoleBinding or ClusterRoleBinding to link them.

Let's assume you have a namespace named my-app-ns. You'll want to grant permissions to deploy applications within this namespace.

Create a file named cicd-rbac.yaml:

apiVersion: v1
kind: Namespace
metadata:
  name: my-app-ns
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: github-actions-sa
  namespace: my-app-ns
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: github-actions-role
  namespace: my-app-ns
rules:
- apiGroups: [", "apps", "extensions", "batch", "networking.k8s.io"] # Add other API groups as needed
  resources: ["pods", "deployments", "services", "ingresses", "jobs", "configmaps", "secrets", "persistentvolumeclaims", "statefulsets", "daemonsets"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: github-actions-binding
  namespace: my-app-ns
subjects:
- kind: ServiceAccount
  name: github-actions-sa
  namespace: my-app-ns
roleRef:
  kind: Role
  name: github-actions-role
  apiGroup: rbac.authorization.k8s.io
Apply this configuration to your cluster:

kubectl apply -f cicd-rbac.yaml
Step 2: Get the Service Account Token

Kubernetes automatically creates a secret for the Service Account that contains its token. You can retrieve this token.

kubectl get secret github-actions-sa-token-xxxxx -n my-app-ns -o jsonpath='{.data.token}' | base64 --decode
Note: The secret name might vary. You can find it by running kubectl get secrets -n my-app-ns and looking for a secret related to github-actions-sa.

Step 3: Store the Token as a GitHub Secret

In your GitHub repository, navigate to Settings > Secrets and variables > Actions. Click New repository secret. Name it KUBE_CONFIG_DATA (or similar) and paste the decoded token value into the secret field. This token will be securely injected into your GitHub Actions workflow.

Deploying Applications to Kubernetes from CI/CD using kubectl
With authentication established, the next logical step is to deploy your application to Kubernetes. The kubectl command-line tool is the primary interface for interacting with a Kubernetes cluster, and it's a cornerstone of automated deployments within CI/CD pipelines.

What is kubectl?

kubectl is a command-line tool for communicating with a Kubernetes cluster's API server. It allows you to deploy applications, inspect and manage cluster resources, and view logs. In a CI/CD context, kubectl commands are executed within the pipeline's job steps.

Why use kubectl for Deployments?

Direct Control: Provides granular control over Kubernetes resources.
Ubiquitous: It's the standard tool for Kubernetes management.
Flexibility: Can be used to apply raw YAML manifests, perform imperative commands, and manage rolling updates.
Integration: Easily integrated into shell scripts and CI/CD workflows.
How to Deploy Applications with kubectl in CI/CD:

The general workflow involves:

Ensuring your application's Docker image is built and pushed to a container registry.
Having Kubernetes manifest files (YAML) that define your application's Deployment, Service, Ingress, etc.
Using kubectl commands within your CI/CD pipeline to apply these manifests or update existing resources.
Lab: Update the GitHub Actions workflow to deploy the Dockerized application to Kubernetes using `kubectl`.

Let's assume you have a simple web application, Dockerized, and its image is available in a registry (e.g., GitHub Container Registry or Docker Hub). You also have a k8s/deployment.yaml and k8s/service.yaml file in your repository.

Prerequisites:

A GitHub repository with your application code.
A Dockerfile for your application.
A GitHub Actions workflow file (e.g., .github/workflows/deploy.yml) that builds and pushes the Docker image.
Kubernetes manifests (deployment.yaml, service.yaml) in a directory (e.g., k8s/).
A configured Kubernetes cluster with authentication set up as described in the previous section.
Step 1: Create Kubernetes Manifests

Ensure you have your Kubernetes manifests. Here are basic examples:

k8s/deployment.yaml:

Step 2: Modify your GitHub Actions Workflow

We'll add steps to apply these manifests and potentially update the image tag.

Here's an extended version of the .github/workflows/deploy.yml file:

name: Deploy to Kubernetes

on:
  push:
    branches:
      - main

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Log in to Docker Hub (or your registry)
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }} # Tag with commit SHA for traceability
          # If using GitHub Container Registry (GHCR):
          # tags: ghcr.io/${{ github.repository_owner }}/your-app-name:${{ github.sha }}

  deploy:
    runs-on: ubuntu-latest
    needs: build-and-push # Ensure build and push is complete before deploying
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Configure kubectl
        run: |
          # ... (kubectl configuration steps from previous section) ...
          K8S_SERVER="https://your-kubernetes-api-server.example.com" # Replace
          K8S_CA_CERT="-----BEGIN CERTIFICATE-----
YOUR_BASE64_ENCODED_CA_CERT
-----END CERTIFICATE-----" # Replace

          kubectl config set-cluster k8s-cluster 
            --server=${K8S_SERVER} 
            --certificate-authority=<(echo -e "${K8S_CA_CERT}") 
            --embed-certs=true

          kubectl config set-credentials github-actions-user 
            --token=${{ secrets.KUBE_CONFIG_DATA }}

          kubectl config set-context github-actions-context 
            --cluster=k8s-cluster 
            --user=github-actions-user 
            --namespace=my-app-ns

          kubectl config use-context github-actions-context

      - name: Deploy application manifests
        run: |
          # Apply the service first, as deployments might depend on it
          kubectl apply -f k8s/service.yaml

          # Apply the deployment. The image tag will be updated in the next step.
          kubectl apply -f k8s/deployment.yaml

      - name: Update deployment image
        run: |
          # This command updates the image of the 'web-app-container' in the 'my-web-app' deployment
          # to the newly built Docker image tagged with the commit SHA.
          kubectl set image deployment/my-web-app web-app-container=YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }} --record
          # If using GHCR:
          # kubectl set image deployment/my-web-app web-app-container=ghcr.io/${{ github.repository_owner }}/your-app-name:${{ github.sha }} --record

      - name: Verify deployment
        run: |
          kubectl rollout status deployment/my-web-app
          kubectl get pods -l app=my-web-app
          kubectl get service my-web-app-service
Explanation of Key Steps:

build-and-push job: This job (which must complete before deploy) builds your Docker image and pushes it to your registry, tagging it with the Git commit SHA (${{ github.sha }}). This is a best practice for traceability.
deploy job:
Configure kubectl: Sets up the Kubernetes context using the secrets you've stored.
Deploy application manifests: kubectl apply -f k8s/service.yaml and kubectl apply -f k8s/deployment.yaml create or update the resources defined in your YAML files. If the resources do not exist, they are created. If they do, kubectl apply attempts to reconcile the desired state with the current state.
Update deployment image: kubectl set image deployment/my-web-app web-app-container=... is a crucial command. It tells Kubernetes to update the specified container within the specified deployment to use the new Docker image. The --record flag adds an annotation to the deployment history, useful for rollbacks.
Verify deployment: kubectl rollout status and kubectl get pods/service are used to confirm that the deployment was successful and the application is running as expected.
Real-World Scenarios:

Blue/Green Deployments: While kubectl set image performs a rolling update by default, more advanced strategies like blue/green or canary deployments can be orchestrated by managing multiple deployments and updating load balancer/ingress rules.
Configuration Management: Use ConfigMaps and Secrets to manage application configurations and sensitive data, and deploy them alongside your application.
Environment Promotion: The same pipeline can be adapted to deploy to different environments (dev, staging, prod) by changing the Kubernetes context or namespace.
Using kubectl directly provides a powerful and flexible way to manage your Kubernetes deployments within your CI/CD pipeline. However, for more complex applications, managing numerous YAML files can become cumbersome. This is where Helm comes into play.

Managing Kubernetes Manifests with CI/CD
As your Kubernetes deployments grow in complexity, managing individual YAML manifest files for every resource can become challenging. Keeping track of versions, dependencies, and environment-specific configurations requires a robust strategy. CI/CD pipelines play a vital role in managing these manifests effectively.

What are Kubernetes Manifests?

Kubernetes manifests are YAML or JSON files that describe the desired state of Kubernetes objects, such as Pods, Deployments, Services, ConfigMaps, Secrets, and Ingresses. They are the declarative way to define what you want to run in your cluster.

Why is Manifest Management Important in CI/CD?

Version Control: Manifests should be version-controlled alongside your application code, enabling reproducibility and auditability.
Environment Specificity: Different environments (development, staging, production) often require different configurations (e.g., replica counts, resource limits, ingress hostnames).
Consistency: Ensures that deployments are consistent across all environments.
Automation: CI/CD pipelines automate the process of applying these manifests.
Strategies for Managing Kubernetes Manifests:

Several approaches can be employed within a CI/CD pipeline:

Raw YAML Files with `kubectl apply`: As demonstrated in the previous section, you can store your YAML files in your repository and use kubectl apply -f  to deploy them. This is simple for basic deployments but lacks templating and advanced dependency management.
Templating Tools (e.g., Kustomize, Helm): These tools allow you to define base configurations and then overlay environment-specific customizations.
GitOps Tools (e.g., Argo CD, Flux CD): These tools automate deployments by continuously monitoring a Git repository for changes in manifests and reconciling them with the cluster state.
Using Kustomize for Manifest Management

Kustomize is a template-free way to customize Kubernetes configurations. It works by overlaying patches onto a base set of YAML files. This is often integrated directly into kubectl (kubectl apply -k ).

Example Kustomize Structure:

base/
  deployment.yaml
  service.yaml
overlays/
  development/
    kustomization.yaml
    deployment-patch.yaml # e.g., increase replicas, change image tag
  production/
    kustomization.yaml
    deployment-patch.yaml # e.g., different resource limits, ingress config
In your CI/CD pipeline, you would use:

# For development environment
kubectl apply -k overlays/development/

# For production environment
kubectl apply -k overlays/production/
Using Helm for Manifest Management (Optional Lab)

Helm is a package manager for Kubernetes. It uses charts, which are collections of pre-configured Kubernetes resource definitions. Helm charts allow you to define, install, and upgrade even the most complex Kubernetes applications.

Why Helm?

Templating: Charts use Go templating to allow dynamic configuration.
Packaging: Charts package all related Kubernetes resources into a single unit.
Reusability: Easily share and reuse charts.
Release Management: Helm tracks releases, making rollbacks straightforward.

# ... other parts of deployment.yaml ...
spec:
  replicas: {{ .Values.replicaCount }}

    matchLabels:

      labels:
        app: {{ include "my-web-app-chart.name" . }}
        release: {{ .Release.Name }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 80
              protocol: TCP
          # ... resources, livenessProbe, etc. ...

          kubectl get service my-web-app-service -n my-app-ns
Key Helm Commands in CI/CD:

helm upgrade --install : This command installs the chart if the release does not exist, or upgrades it if it does. It's ideal for CI/CD as it handles both initial deployments and subsequent updates.
--set key=value: Allows you to override values defined in values.yaml directly from the command line. This is how we pass the dynamic Docker image tag.
--namespace : Specifies the Kubernetes namespace for the deployment.
--create-namespace: Ensures the namespace exists before deployment.
Managing Kubernetes manifests effectively is crucial for scalable and maintainable deployments. While raw YAML is suitable for simple cases, tools like Kustomize and Helm provide powerful templating and customization capabilities that are essential for complex applications and multi-environment strategies.

Rolling Out New Versions of Applications
A critical aspect of CI/CD for Kubernetes is the ability to roll out new versions of your application without causing downtime or negatively impacting user experience. Kubernetes Deployments provide built-in mechanisms for managing these updates, and CI/CD pipelines orchestrate their execution.

What is a Rolling Update?

A rolling update is the default deployment strategy in Kubernetes. It gradually updates Pods in a Deployment by terminating existing Pods and creating new ones, ensuring that a specified number of Pods are always available. This minimizes downtime and allows for a smooth transition to the new version.

Why are Controlled Rollouts Essential?

Zero Downtime: The primary goal is to keep the application available throughout the update process.
Risk Mitigation: If a new version has issues, the impact is limited, and rollback is easier.
User Experience: Users experience a continuous service without interruptions.
Automation: CI/CD pipelines automate the complex process of managing these updates.
Kubernetes Deployment Strategies for Rollouts:

The spec.strategy field in a Kubernetes Deployment object defines how updates are performed. The two main strategies are:

RollingUpdate (Default):
maxUnavailable: The maximum number of Pods that can be unavailable during the update.
maxSurge: The maximum number of Pods that can be created over the desired number of Pods.
For example, if you have replicas: 3, maxUnavailable: 1, and maxSurge: 1:

Kubernetes will terminate one old Pod.
Then, it will create one new Pod.
This process repeats until all old Pods are replaced by new ones. At any point, at least 2 Pods (3 - 1) are available, and at most 4 Pods (3 + 1) exist.
Recreate: This strategy terminates all existing Pods before creating new ones. This results in downtime and is generally not recommended for production environments unless absolutely necessary.
Orchestrating Rolling Updates via CI/CD:

When you use kubectl set image or helm upgrade with a new image tag, Kubernetes automatically triggers a rolling update based on the Deployment's strategy. Your CI/CD pipeline's role is to:

Build and push the new Docker image with a unique tag (e.g., commit SHA, semantic version).
Trigger the deployment command (kubectl set image or helm upgrade) with the new image tag.
Monitor the rollout status to ensure success or trigger alerts/rollbacks if it fails.
Example: Using `kubectl rollout` commands

While kubectl set image is common, you can also use more explicit rollout commands:

1. Updating the Image:

This is the same as before, but it's the trigger for the rolling update.

kubectl set image deployment/my-web-app web-app-container=YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }} --record
2. Monitoring Rollout Status:

This command waits until the deployment has successfully rolled out or times out.

kubectl rollout status deployment/my-web-app
If the rollout fails (e.g., new Pods crash or fail readiness probes), this command will exit with an error, which your CI/CD pipeline can catch.

3. Rolling Back to a Previous Version:

If a deployment fails or a new version introduces critical bugs, you can easily roll back to a previous revision.

First, check the deployment history:

kubectl rollout history deployment/my-web-app
Then, roll back to a specific revision (e.g., revision 2):

kubectl rollout undo deployment/my-web-app --to-revision=2
Your CI/CD pipeline can be configured to automatically trigger a rollback if the rollout status check fails.

Advanced Rollout Strategies:

While rolling updates are standard, more sophisticated strategies can be implemented:

Canary Deployments: Gradually shift traffic to the new version for a small subset of users. If the new version performs well, gradually increase the traffic. This can be achieved by managing multiple deployments and updating Ingress rules or Service selectors.
Blue/Green Deployments: Deploy the new version alongside the old one (blue and green environments). Once the new version is ready, switch traffic from the old to the new version instantly. This offers instant rollback but requires more resources.
These advanced strategies often involve additional tooling or more complex Kubernetes configurations (e.g., using an Ingress controller with traffic splitting capabilities, or service meshes like Istio).

Best Practices for Rollouts:

Use Unique Image Tags: Always tag your Docker images with unique identifiers (commit SHA, semantic version) to ensure you're deploying the intended version and for easy rollback. Avoid using latest in production.
Implement Readiness and Liveness Probes: These Kubernetes probes are essential for the rolling update strategy. Liveness probes tell Kubernetes when to restart a container, and readiness probes tell Kubernetes when a container is ready to serve traffic. Without them, Kubernetes might consider a Pod "ready" before your application is actually functional.
Automate Rollback: Configure your CI/CD pipeline to automatically roll back to the previous stable version if the rollout status indicates failure.
Monitor Closely: Implement robust monitoring and alerting for your applications. This will help you detect issues during or after a rollout quickly.
By leveraging Kubernetes' built-in deployment strategies and orchestrating them through your CI/CD pipeline, you can achieve safe, reliable, and automated application updates.

GitOps Integration with CI/CD for Kubernetes
GitOps represents a paradigm shift in how we manage infrastructure and application deployments. It extends DevOps principles to infrastructure automation by using Git as the single source of truth for declarative infrastructure and applications. When integrated with CI/CD, GitOps provides a powerful, auditable, and automated way to manage Kubernetes deployments.

What is GitOps?

GitOps is an operational framework that takes DevOps best practices used for application development, such as version control, collaboration, and compliance, and applies them to infrastructure automation. In a GitOps model:

The desired state of your infrastructure and applications is declared in Git.
An automated process ensures that the live environment matches the state declared in Git.
Any changes to the live environment are made by committing changes to Git, which then triggers the automated reconciliation process.
Key Principles of GitOps:

Declarative: The entire system state is described declaratively.
Versioned and Immutable: The desired state is stored in Git, providing version history and immutability.
Pulled Automatically: Approved changes to the desired state are automatically applied to the system.
Continuously Reconciled: Software agents ensure the live state matches the desired state in Git.
How CI/CD and GitOps Work Together:

While GitOps focuses on the reconciliation of the desired state (in Git) with the actual state (in the cluster), CI/CD pipelines are often used to trigger the GitOps process or to prepare the declarative manifests that GitOps tools consume.

There are two primary patterns for integrating CI/CD with GitOps:

CI/CD Pushes to GitOps Repo:
Your traditional CI/CD pipeline (e.g., GitHub Actions) builds your Docker image.
It then updates the Kubernetes manifests (e.g., Deployment YAML) in a separate Git repository (the GitOps repository). This update might involve changing the image tag.
A GitOps agent (like Argo CD or Flux CD) running in your Kubernetes cluster monitors this GitOps repository.
When it detects a change, it pulls the updated manifests and applies them to the cluster.
CI/CD Triggers GitOps Agent (Less Common for Pure GitOps):
Your CI/CD pipeline builds the Docker image.
Instead of pushing to a GitOps repo, it might directly trigger a GitOps agent (e.g., via an API call) to perform the deployment. This is less "pure" GitOps as the Git repo is not the sole driver of change, but it can be a practical hybrid approach.
Demo: Illustrate how CI/CD can trigger GitOps workflows.

Let's illustrate the first, more common pattern: CI/CD pushing changes to a GitOps repository, which is then managed by a GitOps tool.

Scenario:

Application Repo: Contains your application code and Dockerfile.
GitOps Repo: Contains your Kubernetes manifests (Deployment, Service, etc.) managed by Helm or Kustomize.
CI/CD Pipeline (GitHub Actions): Runs on the Application Repo, builds the Docker image, and pushes the updated manifest (with new image tag) to the GitOps Repo.
GitOps Tool (Argo CD): Runs in your Kubernetes cluster, monitors the GitOps Repo, and syncs changes to the cluster.
Step 1: Set up the GitOps Repository

Create a new GitHub repository (e.g., my-k8s-gitops). Inside this repository, structure your Kubernetes manifests. For this demo, let's use a simple Deployment YAML.

my-k8s-gitops/apps/my-web-app/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web-app
  labels:
    app: my-web-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-web-app
  template:
    metadata:
      labels:
        app: my-web-app
    spec:
      containers:
      - name: web-app-container
        image: YOUR_DOCKER_REGISTRY/your-app-name:v1.0.0 # Initial version
        ports:
        - containerPort: 80
Commit and push this initial manifest to your my-k8s-gitops repository.

Step 2: Install a GitOps Tool (e.g., Argo CD)

Follow the official documentation to install Argo CD in your Kubernetes cluster. This typically involves applying a set of YAML manifests provided by Argo CD.

kubectl create namespace argocd

kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

Once installed, you'll need to configure Argo CD to connect to your GitOps repository. This involves creating an Application resource in Kubernetes that tells Argo CD which Git repository to watch and which path within that repository contains the manifests.

argocd-app.yaml:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-web-app-app
  namespace: argocd # Argo CD's namespace
spec:
  project: default
  source:
    repoURL: https://github.com/YOUR_GITHUB_USERNAME/my-k8s-gitops.git # Replace with your GitOps repo URL
    path: apps/my-web-app # Path to your manifests within the repo
    targetRevision: HEAD # Or a specific branch like 'main'
  destination:
    server: https://kubernetes.default.svc # Target cluster URL
    namespace: my-app-ns # Target namespace for the application
  syncPolicy:
    automated: # Enable automated sync
      prune: true # Automatically delete resources not present in Git
      selfHeal: true # Automatically sync if cluster state drifts from Git
    syncOptions:
    - CreateNamespace=true # Create the target namespace if it does not exist
Apply this to your cluster:

kubectl apply -f argocd-app.yaml
Argo CD will now detect the manifests in your GitOps repository and deploy them to the specified namespace.

Step 3: Modify the CI/CD Pipeline (Application Repo)

Update your GitHub Actions workflow in your application repository to push changes to the GitOps repository.

name: CI/CD to GitOps

on:
  push:
    branches:
      - main

jobs:
  build-and-update-gitops:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout application code
        uses: actions/checkout@v4

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push Docker image
        id: docker_build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }}

      - name: Checkout GitOps repository
        uses: actions/checkout@v4
        with:
          repository: YOUR_GITHUB_USERNAME/my-k8s-gitops # Replace with your GitOps repo
          token: ${{ secrets.GIT_OPS_REPO_PAT }} # A Personal Access Token for the GitOps repo

      - name: Update Kubernetes manifest with new image tag
        run: |
          # Navigate to the directory containing the deployment.yaml in the GitOps repo
          cd apps/my-web-app

          # Use sed to update the image tag in deployment.yaml
          # Ensure your Docker registry and image name match
          sed -i "s|image: YOUR_DOCKER_REGISTRY/your-app-name:.*|image: YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }}|g" deployment.yaml

          # Commit and push the changes
          git config --global user.name 'GitHub Actions Bot'
          git config --global user.email 'actions-bot@github.com'
          git add .
          git commit -m "Update my-web-app image to ${{ github.sha }}"
          git push

      - name: Notify GitOps tool (Optional - Argo CD syncs automatically)
        # In a pure GitOps setup, Argo CD automatically detects changes.
        # However, you might have custom triggers or notifications.
        run: echo "Change pushed to GitOps repo. Argo CD will sync automatically."
Important Notes for the Demo:

GIT_OPS_REPO_PAT: You'll need to create a GitHub Personal Access Token (PAT) with `repo` scope for your my-k8s-gitops repository and add it as a secret in your application repository.
sed command: This command is a simple way to update the image tag. For more complex manifest updates or Helm charts, you might use tools like yq or Helm commands to modify the values.
Automatic Sync: The key to this GitOps pattern is that Argo CD (or Flux CD) is configured to automatically sync changes from the GitOps repository. Once the CI/CD pipeline pushes the updated manifest, Argo CD detects the change and applies it to the cluster.
Benefits of GitOps with CI/CD:

Single Source of Truth: Git is the definitive source for your infrastructure and application state.
Auditing and Rollback: Git history provides a clear audit trail of all changes, making rollbacks straightforward.
Enhanced Security: Changes are reviewed via Git pull requests, and automated agents apply them, reducing direct access to the cluster.
Consistency: Ensures that the cluster state always reflects what's defined in Git.
GitOps, when combined with CI/CD, offers a robust and auditable approach to managing Kubernetes deployments, significantly improving reliability and operational efficiency.

Practical Application: Building a Complete Deployment Pipeline
In this section, we'll consolidate the concepts learned and outline the steps to build a more complete end-to-end CI/CD pipeline for deploying a Dockerized application to Kubernetes. This will involve integrating Docker builds, authentication, and deployment using kubectl.

Scenario Recap:

We have a simple web application. The goal is to:

Build a Docker image for the application on every push to the main branch.
Push this image to a container registry (e.g., Docker Hub or GHCR).
Deploy this image to a Kubernetes cluster using kubectl, ensuring secure authentication.
Verify the deployment.
Prerequisites:

A GitHub repository containing your application code and a Dockerfile.
A Kubernetes cluster accessible via kubectl.
A Service Account with appropriate RBAC permissions configured in your Kubernetes cluster for CI/CD.
The Service Account token stored as a GitHub Secret (e.g., KUBE_CONFIG_DATA).
Your Kubernetes cluster's API server endpoint and CA certificate data (for manual kubectl configuration).
A container registry account (Docker Hub, GHCR) and credentials stored as GitHub Secrets (e.g., DOCKERHUB_USERNAME, DOCKERHUB_TOKEN).
Kubernetes manifest files (deployment.yaml, service.yaml) in your repository (e.g., in a k8s/ directory).
Step-by-Step Implementation Guide:

Step 1: Prepare Your Application Repository

Ensure your repository has:

Dockerfile: To build your application's image.
k8s/deployment.yaml: Defines your application's deployment.
k8s/service.yaml: Defines how your application is exposed.
.github/workflows/deploy.yml: Your GitHub Actions workflow file.
Step 2: Configure GitHub Secrets

In your GitHub repository's Settings > Secrets and variables > Actions, add the following secrets:

KUBE_CONFIG_DATA: Your Kubernetes Service Account token.
DOCKERHUB_USERNAME: Your Docker Hub username.
DOCKERHUB_TOKEN: Your Docker Hub access token or password.
K8S_SERVER: Your Kubernetes API server endpoint (e.g., https://your-kubernetes-api-server.example.com).
K8S_CA_CERT: Your base64 encoded CA certificate for the cluster.
Step 3: Create/Update the GitHub Actions Workflow File

Create or modify .github/workflows/deploy.yml with the following content. This workflow combines building, pushing, and deploying.

name: Full CI/CD Pipeline to Kubernetes

on:
  push:
    branches:
      - main # Trigger on pushes to the main branch

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push Docker image
        id: docker_build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }} # Tag with commit SHA
          # Example for GHCR:
          # tags: ghcr.io/${{ github.repository_owner }}/your-app-name:${{ github.sha }}

      - name: Configure kubectl
        run: |
          # Install kubectl if not present (usually pre-installed on GitHub runners)
          # curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
          # chmod +x kubectl
          # sudo mv kubectl /usr/local/bin/

          kubectl config set-cluster k8s-cluster 
            --server=${{ secrets.K8S_SERVER }} 
            --certificate-authority=<(echo -e "${{ secrets.K8S_CA_CERT }}") 
            --embed-certs=true

          kubectl config set-credentials github-actions-user 
            --token=${{ secrets.KUBE_CONFIG_DATA }}

          kubectl config set-context github-actions-context 
            --cluster=k8s-cluster 
            --user=github-actions-user 
            --namespace=my-app-ns # Ensure this namespace exists or is created

          kubectl config use-context github-actions-context

      - name: Deploy application manifests
        run: |
          # Apply the service first
          kubectl apply -f k8s/service.yaml

          # Apply the deployment. The image tag will be updated in the next step.
          kubectl apply -f k8s/deployment.yaml

      - name: Update deployment image with new tag
        run: |
          # Update the container image to the newly built one
          kubectl set image deployment/my-web-app web-app-container=YOUR_DOCKER_REGISTRY/your-app-name:${{ github.sha }} --record
          # Example for GHCR:
          # kubectl set image deployment/my-web-app web-app-container=ghcr.io/${{ github.repository_owner }}/your-app-name:${{ github.sha }} --record

      - name: Verify deployment rollout
        run: |
          kubectl rollout status deployment/my-web-app --timeout=5m # Wait up to 5 minutes for rollout

      - name: Get deployment details
        run: |
          echo "Deployment successful!"
          kubectl get pods -l app=my-web-app -n my-app-ns
          kubectl get service my-web-app-service -n my-app-ns
Explanation of the Workflow:

Checkout Code: Fetches the latest code from your repository.
Set up Docker Buildx: Prepares the environment for building Docker images.
Log in to Docker Hub: Authenticates with your container registry using stored secrets.
Build and push Docker image: Builds the Docker image and pushes it to the registry, tagged with the Git commit SHA. The id: docker_build allows subsequent steps to reference outputs from this step if needed.
Configure kubectl: This is a critical step where the workflow uses the stored secrets (KUBE_CONFIG_DATA, K8S_SERVER, K8S_CA_CERT) to configure kubectl to connect to your Kubernetes cluster. It sets up a cluster configuration, user credentials, and a context, then switches to that context.
Deploy application manifests: kubectl apply -f k8s/service.yaml and kubectl apply -f k8s/deployment.yaml ensure that your Service and Deployment resources are present in the cluster. If they exist, apply will update them if necessary.
Update deployment image: kubectl set image is the command that triggers the rolling update. It instructs Kubernetes to update the specified container within the my-web-app Deployment to use the newly built Docker image tagged with the commit SHA. The --record flag is useful for tracking deployment history.
Verify deployment rollout: kubectl rollout status is essential for ensuring the deployment was successful. It waits for the deployment to complete and will fail the job if it times out or encounters errors.
Get deployment details: A final step to confirm the deployment by listing the running pods and the service.
Troubleshooting Common Issues:

Authentication Errors: Double-check your KUBE_CONFIG_DATA secret, Service Account permissions (RBAC), and ensure the cluster endpoint and CA cert are correct.
Image Pull Errors: Verify that your Docker image was successfully built and pushed to the registry. Ensure the registry credentials are correct and the image name/tag in the workflow matches the manifest. Check if your Kubernetes cluster has network access to the registry.
Readiness/Liveness Probe Failures: If the kubectl rollout status fails, it's often due to Pods not becoming ready. Ensure your application starts correctly and that your k8s/deployment.yaml includes appropriate readinessProbe and livenessProbe configurations.
Namespace Issues: Ensure the target namespace (e.g., my-app-ns) exists in your Kubernetes cluster or that your deployment strategy creates it.
This comprehensive pipeline automates the entire process from code commit to Kubernetes deployment, embodying the core principles of CI/CD.
