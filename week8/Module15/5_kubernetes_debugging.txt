Deep Dive: Inspecting Pods and Deployments with `kubectl describe`
The kubectl describe command is your primary tool for gaining a comprehensive overview of a Kubernetes resource. When a Pod or Deployment is misbehaving, describe provides a wealth of information that can quickly point you towards the root cause. It's often the first command you'll run when troubleshooting.

What is `kubectl describe`?
kubectl describe allows you to view the detailed state of a specific resource or a group of resources. For Pods, it shows their status, IP address, node assignment, container details (including image, ports, and readiness/liveness probes), volumes, and crucially, a list of recent events associated with that Pod. For Deployments, it reveals the desired number of replicas, the current state, the Pod template, and rollout history.

Why is `kubectl describe` Important?
This command is vital because it consolidates information that might otherwise be scattered across multiple commands or require deep dives into API objects. It provides:

Resource Status: Quickly understand if a Pod is Running, Pending, Failed, or Evicted.
Configuration Details: Verify resource requests/limits, environment variables, and volume mounts.
Node Assignment: See which node a Pod is scheduled on, which is crucial for node-specific issues.
Container State: Examine the state of individual containers within a Pod (e.g., Waiting, Running, Terminated) and their exit codes.
Event Log: The most critical part for debugging, showing a chronological list of events related to the resource's lifecycle, such as scheduling failures, image pull errors, or readiness probe failures.
How to Use `kubectl describe`
The basic syntax is straightforward:

kubectl describe   -n 
Let's break this down:

: This can be pod, deployment, service, ingress, node, etc.
: The specific name of the resource you want to inspect.
-n : (Optional) Specifies the Kubernetes namespace. If omitted, it defaults to the default namespace.
Practical Examples and Scenarios
Scenario 1: A Pod Stuck in `Pending` State
Imagine you've deployed an application, and its Pod is stuck in the Pending state. This usually means Kubernetes cannot schedule the Pod onto a node. Running kubectl describe pod  might reveal events like:

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               ------
  Warning  FailedScheduling  1m    default-scheduler  0/3 nodes are available: 3 Insufficient cpu.
  Warning  FailedScheduling  1m    default-scheduler  0/3 nodes are available: 3 Insufficient memory.
This output clearly indicates that the nodes in your cluster do not have enough CPU or memory resources to accommodate the Pod's requests. You would then need to either reduce the Pod's resource requests or add more resources to your cluster.

Scenario 2: A Deployment Not Rolling Out Correctly
If a Deployment is not updating to the new version of your application, you can inspect it:

kubectl describe deployment <deployment-name>
Look for sections like:

Replicas: (shows desired, updated, available, unavailable)
Pod Template: (shows the container image and configuration)
Conditions: (shows deployment status like Available, Progressing)
Events: (crucial for rollout issues)
Events might show errors like image pull failures, container creation errors, or readiness probe failures preventing new Pods from becoming available.

Scenario 3: A Pod in `CrashLoopBackOff`
When a Pod repeatedly starts and crashes, it enters the CrashLoopBackOff state. kubectl describe pod  will show the container state as Terminated with a non-zero exit code. The events section might provide clues, but the logs are usually more informative for this specific issue. However, describe can confirm the Pod is indeed crashing and provide the exit code.

Unveiling Container Issues: `kubectl logs` Explained
While kubectl describe provides metadata and events, kubectl logs is your direct line to the application's output within a container. This command is indispensable for understanding runtime errors, application-level exceptions, and the general behavior of your application.

What is `kubectl logs`?
kubectl logs retrieves the logs from a container in a Pod. If a Pod has multiple containers, you must specify which container's logs you want to see. These logs are typically the standard output (stdout) and standard error (stderr) streams of your application process running inside the container.

Why is `kubectl logs` Important?
Application logs are the most direct source of information about what your application is doing and why it might be failing. Using kubectl logs allows you to:

Diagnose Application Errors: See stack traces, error messages, and exceptions thrown by your application.
Monitor Application Health: Observe the normal operational output of your application.
Trace Execution Flow: Understand the sequence of operations your application is performing.
Identify Performance Bottlenecks: Sometimes, log messages can indicate slow operations or resource contention within the application itself.
Verify Configuration: Check if your application is starting up with the correct configuration as expected.
How to Use `kubectl logs`
The basic syntax is:

kubectl logs  -n 
Key options and variations:

Specifying a Container: If your Pod has multiple containers, use the -c flag:kubectl logs -c -n 
Following Logs (Live Tail): To stream logs in real-time, use the -f or --follow flag:kubectl logs -f -n 
Previous Logs: If a container has restarted, you can view logs from the previous instance using the -p or --previous flag:kubectl logs -p -n 
Limiting Log Lines: To get only the most recent lines, use --tail:kubectl logs --tail=50 -n 
Timestamps: Add timestamps to log lines with --timestamps=true.
Practical Examples and Scenarios
Scenario 1: Application Crashing on Startup
You deploy a new version of your web application, and the Pod immediately goes into CrashLoopBackOff. You suspect a configuration error or a bug in the new code.

First, you might run kubectl describe pod  to confirm the state. Then, to see why it's crashing, you'd use:

kubectl logs <pod-name>
The output might show something like:

Error: Invalid configuration file 'config.yaml'. Missing required key 'database_url'.
panic: runtime error: invalid memory address or nil pointer dereference
... (stack trace) ...
This clearly indicates a missing configuration parameter, which you can then fix.

Scenario 2: Debugging a Web Server Request Issue
A user reports that they are getting 500 Internal Server Errors when accessing a specific endpoint of your web service. You want to see the logs for the web server Pod.

You can tail the logs to see requests coming in:

kubectl logs -f <web-server-pod-name>
As you or a colleague try to reproduce the error, you'll see log entries. If the application logs an error for that specific request, you'll see it immediately. For example:

2023-10-27 10:30:15 INFO: Request received: GET /api/users/123
2023-10-27 10:30:15 ERROR: Failed to query database: connection refused
2023-10-27 10:30:15 INFO: Responded with 500 Internal Server Error to 192.168.1.100
This points to a database connectivity issue.

Scenario 3: Verifying Background Job Completion
A background worker Pod is supposed to process a queue of tasks. You want to confirm it's running and completing tasks successfully.

You can check the logs:

kubectl logs <worker-pod-name>
You'd look for log messages indicating task processing, success, or any errors encountered during processing.

Interactive Troubleshooting: Executing Commands Inside Containers with `kubectl exec`
Sometimes, inspecting logs and events is not enough. You need to get inside the container to poke around, check file systems, run diagnostic commands, or even manually trigger actions. This is where kubectl exec shines.

What is `kubectl exec`?
kubectl exec allows you to execute a command within a running container in a Pod. It essentially gives you an interactive shell or allows you to run a single command inside the container's environment, just as if you were logged into the machine running the container.

Why is `kubectl exec` Important?
This command is invaluable for deep-dive troubleshooting and interactive debugging:

File System Inspection: Check if configuration files are present, have the correct permissions, or contain the expected data.
Network Diagnostics: Run tools like ping, curl, or netstat from within the container to diagnose network connectivity issues to other services or external endpoints.
Process Inspection: Use commands like ps to see running processes inside the container.
Environment Variable Verification: Check if environment variables are set as expected.
Manual Testing: Execute application-specific commands or scripts to test functionality directly.
Interactive Shell: Obtain a shell (like bash or sh) inside the container for more complex exploration.
How to Use `kubectl exec`
The basic syntax for executing a single command is:

kubectl exec  -c  -n  -- <command> <args...>
Key options and variations:

: The name of the Pod containing the container.
-c : (Required if Pod has multiple containers) Specifies the target container.
-n : The namespace of the Pod.
--: This double dash is important. It separates kubectl options from the command and its arguments that you want to execute inside the container.
: The command to run (e.g., ls, cat, env).
: Any arguments for the command.
For an interactive shell:

kubectl exec -it <pod_name> -c <container_name> -n <namespace> -- /bin/bash
Or, if bash is not available:

kubectl exec -it <pod_name> -c <container_name> -n <namespace> -- /bin/sh
-i or --stdin: Keep STDIN open even if not attached.
-t or --tty: Allocate a pseudo-TTY, which is necessary for interactive shells.
Practical Examples and Scenarios
Scenario 1: Verifying Configuration Files
Your application is failing because it cannot find its configuration file. You suspect the file was not copied correctly into the container image or mounted as a volume.

You can exec into the container and check:

kubectl exec <pod-name> -c <container-name> -- ls -l /app/config/
If the file is missing, the output will reflect that. If it's present, you can then check its contents:

kubectl exec <pod-name> -c <container-name> -- cat /app/config/settings.yaml
Scenario 2: Debugging Network Connectivity
Your application Pod cannot connect to a database Pod. You want to test connectivity from within the application Pod.

First, get an interactive shell:

kubectl exec -it <app-pod-name> -c <app-container-name> -- /bin/bash
Once inside, you can use tools like ping or curl (if installed in the container):

# Inside the container shell
ping <database-service-name>
curl http://<database-service-name>:5432
If these commands fail, it indicates a network issue between the Pods, potentially related to network policies, Service configuration, or DNS resolution.

Scenario 3: Checking Environment Variables
Your application relies on environment variables for configuration (e.g., API keys, database credentials). You want to ensure they are correctly injected.

kubectl exec <pod-name> -c <container-name> -- env
This command will list all environment variables available within the container, allowing you to verify their values.

You will use kubectl exec to get an interactive shell inside the container, inspect its file system, and run diagnostic commands to pinpoint the problem. Direct Access for Testing: Port-Forwarding to Pods
While kubectl exec lets you run commands inside a container, sometimes you need to access the application's network port directly, as if you were a client. kubectl port-forward provides a secure and convenient way to do this, especially during development and debugging.

What is `kubectl port-forward`?
kubectl port-forward establishes a connection between your local machine and a specific port on a Pod (or multiple Pods behind a Deployment, StatefulSet, etc.). It forwards traffic from a port on your local machine to a port on the Pod. This bypasses the need to expose the application via a Service or Ingress for testing purposes.

Why is `kubectl port-forward` Important?
This feature is crucial for:

Local Testing of Remote Applications: Access a database, API, or web application running in a remote Kubernetes cluster directly from your local development environment.
Debugging Network Interactions: Test how your local client applications interact with services running in Kubernetes without deploying them.
Bypassing Complex Networking: Quickly test a Pod's functionality without configuring Services, Ingress controllers, or LoadBalancers.
Security: It creates a secure tunnel, often over TLS, between your machine and the Pod, which is safer than exposing ports directly to the internet.
How to Use `kubectl port-forward`
The basic syntax is:

kubectl port-forward  : -n 
Alternatively, you can forward to a Deployment, StatefulSet, or ReplicaSet:

kubectl port-forward deployment/ : -n 
Key components:

 or deployment/: The target resource. If targeting a Deployment, it will forward to one of the Pods managed by that Deployment.
: The port on your local machine that you will connect to.
: The port that the application is listening on inside the container.
-n : The namespace of the resource.
Important Notes:

This command runs in the foreground. You need to keep the terminal window open. Press Ctrl+C to stop port-forwarding.
You can forward multiple ports simultaneously by specifying them separated by commas: kubectl port-forward ... 8080:80,8443:443
Practical Examples and Scenarios
Scenario 1: Accessing a Database Locally
You have a PostgreSQL database running in a Pod in your Kubernetes cluster, listening on port 5432. You want to connect to it using a local GUI tool like pgAdmin.

Run the following command:

kubectl port-forward postgres-pod 5432:5432 -n database-namespace
Now, in your pgAdmin tool, you can configure a new connection using localhost (or 127.0.0.1) as the host and 5432 as the port. The connection will be securely forwarded to your PostgreSQL Pod.

Scenario 2: Testing a Web API
Your backend API service is running in a Pod and listens on port 8000. You want to test its endpoints using curl or Postman from your local machine.

kubectl port-forward api-deployment 8080:8000 -n api-namespace
After running this, you can make requests to http://localhost:8080, and they will be routed to port 8000 of one of the API Pods.

Scenario 3: Debugging a Microservice
You have a microservice that exposes a health check endpoint on port 9090. You want to quickly check its health status from your local machine.

kubectl port-forward my-microservice-pod 9090:9090 -n microservices
Then, you can run:

curl http://localhost:9090/health

This will allow you to test its functionality from your local machine, simulating how a client would interact with it. Navigating Network Issues: Debugging Services and Ingress
While Pods are the fundamental units of deployment, Services and Ingress controllers are responsible for exposing your applications to the network and enabling communication between them. Debugging issues at this layer is critical for ensuring your applications are reachable and discoverable.

What are Kubernetes Services and Ingress?
Services: A Kubernetes Service is an abstraction that defines a logical set of Pods and a policy by which to access them. It provides a stable IP address and DNS name for a group of Pods, acting as a load balancer. Services are essential for inter-Pod communication and for exposing applications outside the cluster (e.g., NodePort, LoadBalancer types).

Ingress: An Ingress controller manages external access to Services within a cluster, typically HTTP and HTTPS. It provides features like load balancing, SSL termination, and name-based virtual hosting. An Ingress resource defines the rules for routing external traffic to internal Services.

Why is Debugging Services and Ingress Important?
Problems with Services or Ingress can lead to applications being unreachable, incorrect routing, or connection failures. Debugging these components helps you:

Ensure Reachability: Verify that external traffic can reach your application.
Diagnose Routing Issues: Understand why traffic is not being directed to the correct Pods or Services.
Troubleshoot Load Balancing: Identify if traffic is being unevenly distributed or if certain Pods are not receiving traffic.
Resolve DNS Problems: Ensure that Service names are resolving correctly within the cluster.
Validate SSL/TLS Configuration: For Ingress, check certificate issues and secure connections.
How to Debug Services with `kubectl`
1. Inspect the Service: Use kubectl describe service .

Look at the Selector field: Ensure it correctly matches the labels on your Pods.
Check Endpoints: This shows the IP addresses and ports of the Pods that the Service is currently directing traffic to. If this is empty, the Service is not finding any matching Pods.
Examine Type: Understand how the Service is exposed (ClusterIP, NodePort, LoadBalancer).
2. Check Pod Labels: Ensure the Pods you expect to be targeted by the Service have labels that match the Service's selector.

kubectl get pods --show-labels -n <namespace>
3. Verify Pod Readiness: Ensure the Pods are running and ready. A Service will typically only send traffic to ready Pods.

kubectl get pods -n <namespace>
4. Test Connectivity from Another Pod: Use kubectl exec to run a command from another Pod in the cluster to try and reach the Service name.

kubectl exec -it <another-pod-name> -n <namespace> -- /bin/bash
Inside the shell:

# Try to resolve the service name (DNS)
nslookup <service-name>

# Try to connect to the service's ClusterIP and port
curl http://<service-cluster-ip>:<service-port>
How to Debug Ingress with `kubectl`
1. Inspect the Ingress Resource: Use kubectl describe ingress .

Check the Rules: Verify that the hostnames and paths are configured correctly.
Examine Backend: Ensure the default backend and specific rules point to the correct Service and port.
Look at Annotations: Many Ingress controllers use annotations for specific configurations (e.g., SSL redirect, rewrite rules). Ensure these are correct.
Review Events: Similar to Pods, Ingress resources can have events indicating configuration problems or issues with the Ingress controller itself.
2. Inspect the Ingress Controller Pod(s): The Ingress controller is itself a set of Pods (e.g., Nginx Ingress Controller, Traefik). You need to check their logs and status.

kubectl logs -l app.kubernetes.io/name=ingress-nginx -n ingress-nginx
(The label and namespace will vary depending on your Ingress controller installation.) Look for errors related to configuration reloads, backend connectivity, or certificate issues.

3. Verify Backend Service and Pods: Ensure the Service and Pods that the Ingress is routing to are healthy and accessible.

4. Check DNS: Ensure that the hostname configured in your Ingress rule points to the external IP address of your Ingress controller (often a LoadBalancer IP).

Practical Examples and Scenarios
Scenario 1: Application Not Accessible Externally
You've deployed a web application, and it works fine when accessed via kubectl port-forward, but it's not reachable from outside the cluster.

Debugging Steps:

Check Ingress: kubectl describe ingress my-app-ingress. Does the hostname and path match what you're trying to access? Does the backend Service and port look correct?
Check Service: kubectl describe service my-app-service. Are the selectors correct? Are there endpoints listed?
Check Pods: kubectl get pods -l app=my-app. Are the Pods running and ready? Do their labels match the Service selector?
Check Ingress Controller Logs: kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx. Look for errors related to your specific hostname or backend Service.
Scenario 2: Incorrect Routing
You have two applications, app-a and app-b, both exposed via Ingress rules on different paths (e.g., /app-a and /app-b). Users are reporting that requests to /app-a are sometimes served by app-b.

Debugging Steps:

Review Ingress Rules: kubectl describe ingress my-ingress. Ensure the path matching is precise and that there are no overlapping or ambiguous rules.
Check Service Selectors: Verify that the selectors for app-a-service and app-b-service are distinct and correctly target their respective Pods.
Examine Ingress Controller Configuration: Some Ingress controllers have specific configurations for path matching (e.g., prefix vs. exact match). Consult your controller's documentation.
Connecting to Prometheus and Grafana
While not directly part of kubectl debugging, Services and Ingress are often monitored by tools like Prometheus and Grafana. You might use kubectl get service to find the Service name for your Prometheus or Grafana instance, or kubectl port-forward to access their dashboards locally for monitoring metrics related to network traffic, request rates, and error rates, which can provide further clues during debugging.

Understanding Kubernetes Events for Contextual Debugging
Kubernetes events are a crucial, often overlooked, source of information for understanding the lifecycle and state of your cluster's resources. They provide a chronological record of significant occurrences, from Pod scheduling to container restarts and network issues.

What are Kubernetes Events?
Kubernetes events are objects that record the lifecycle of various Kubernetes resources. They are generated by the Kubernetes control plane (e.g., scheduler, controller-manager) and by kubelets on nodes. Events are typically used to provide insights into why a resource is in a particular state, especially when it's not behaving as expected.

Why are Kubernetes Events Important?
Events offer invaluable context for debugging:

Root Cause Analysis: They often pinpoint the exact reason a Pod failed to schedule, a container couldn't start, or a Service couldn't be created.
Lifecycle Tracking: Understand the sequence of actions that led to the current state of a resource.
Early Warning System: Detect potential issues before they cause major disruptions.
Troubleshooting Automation: Events can be programmatically monitored to trigger alerts or automated remediation actions.
How to View Kubernetes Events
The primary command to view events is kubectl get events.

Viewing Events for a Specific Namespace:

kubectl get events -n <namespace>
Viewing Events for All Namespaces:

kubectl get events --all-namespaces
Viewing Events for a Specific Resource:

As we saw with kubectl describe, events are often displayed directly within the output for a specific resource. However, you can also filter events related to a particular Pod, Deployment, or other resource:

kubectl describe pod <pod-name> -n <namespace>
The Events section at the bottom of the describe output is the most common way to see relevant events.

Understanding Event Fields:

LAST SEEN: How long ago the event occurred.
TYPE: Indicates if the event is a Normal occurrence or a Warning. Warnings are usually indicative of problems.
REASON: A short, machine-readable identifier for the event (e.g., FailedScheduling, ImagePullBackOff, Unhealthy).
OBJECT: The name of the object the event pertains to.
MESSAGE: A human-readable description of the event.
Practical Examples and Scenarios
Scenario 1: Pod Stuck in `Pending`
You run kubectl get pods and see a Pod stuck in Pending. You then run:

kubectl describe pod <pending-pod-name>
The events section might show:

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               ------
  Warning  FailedScheduling  2m    default-scheduler  0/3 nodes are available: 3 Insufficient cpu.
This event clearly tells you the scheduler couldn't find a node with enough CPU. This is a direct pointer to resource constraints.

Scenario 2: Container Failing to Start
A Pod is created, but its containers are not starting, and the Pod status is not Running.

kubectl describe pod <pod-name>
You might see events like:

Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               ------
  Warning  Failed     5m (x3 over 10m)   kubelet            Error: Image 'my-private-registry/my-app:latest' not found
  Warning  BackOff    2m (x5 over 8m)    kubelet            Back-off restarting failed container
This indicates an ImagePullBackOff, meaning Kubernetes couldn't pull the specified container image. This could be due to an incorrect image name, a typo, or missing image pull secrets.

Scenario 3: Service Not Finding Endpoints
You've created a Service, but when you check its endpoints, it's empty.

kubectl describe service <service-name>
The Endpoints field is . You then check the events for the Service itself (if any) or, more importantly, the events for the Pods it's supposed to target.

kubectl get events --field-selector involvedObject.name=<service-name> -n <namespace>
If there are no direct Service events, you'd look at the Pod events. If the Pods have labels that do not match the Service selector, or if the Pods are in a CrashLoopBackOff or Error state, the Service will not be able to find healthy endpoints.

Connecting Events to Other Tools
While kubectl get events is the primary way to view them, events are also accessible via the Kubernetes API. Tools like Prometheus can scrape events (though this requires specific configurations or exporters) and visualize them in Grafana. This allows for more advanced monitoring and alerting based on event types and frequencies.

Common Kubernetes Troubleshooting Scenarios and `kubectl` Solutions
In this section, we'll consolidate our knowledge by walking through common failure scenarios in Kubernetes and demonstrating how the kubectl commands we've learned can be applied to diagnose and resolve them. This practical application is key to building robust debugging skills.

Scenario 1: Pod Stuck in `CrashLoopBackOff`
Symptom: A Pod repeatedly restarts, and its status shows CrashLoopBackOff.

Diagnosis Steps:

Check Pod Status and Events:
kubectl get pods -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
Look for Terminated state with a non-zero exit code in the container status, and any relevant events like BackOff or specific error messages.
Examine Container Logs:
kubectl logs <pod-name> -n <namespace>
If the container restarted, check previous logs:
kubectl logs -p <pod-name> -n <namespace>
The logs will usually contain the application's error message or stack trace.
Common Causes & Solutions:

Application Error: Bug in the application code. Fix the code and redeploy.
Configuration Error: Incorrect configuration file, missing environment variables, or invalid parameters. Use kubectl exec to inspect files/env vars, or kubectl logs to see startup errors.
Resource Limits Too Low: Application crashes due to insufficient CPU/memory. Adjust resource requests/limits in the Deployment.
Dependency Issues: Application fails because a required service (e.g., database) is unavailable or misconfigured. Use kubectl exec to test connectivity.
Scenario 2: Pod Stuck in `Pending`
Symptom: A Pod remains in the Pending state indefinitely.

Diagnosis Steps:

Describe the Pod:
kubectl describe pod <pod-name> -n <namespace>
The Events section is critical here. Look for FailedScheduling messages.
Common Causes & Solutions:

Insufficient Resources: Nodes lack sufficient CPU, memory, or GPU. The event message will specify this (e.g., Insufficient cpu). Solution: Increase cluster resources or reduce Pod resource requests.
Node Affinity/Anti-Affinity Rules: Pod cannot be scheduled due to complex scheduling rules. Examine the Pod's spec.affinity and spec.nodeSelector.
Taints and Tolerations: Nodes may have taints that the Pod does not tolerate. Check node taints with kubectl describe node  and Pod tolerations.
Persistent Volume Issues: If the Pod requires a Persistent Volume (PV) that cannot be provisioned or attached, it may remain pending. Check PV/PVC status and events.
Scenario 3: Service Not Discoverable / No Endpoints
Symptom: Applications cannot reach a Service, or kubectl describe service shows no endpoints.

Diagnosis Steps:

Describe the Service:
kubectl describe service <service-name> -n <namespace>
Verify the Selector field.
Check Pod Labels: Ensure Pods have labels matching the Service selector.
kubectl get pods --show-labels -n <namespace>
Check Pod Status: Ensure the Pods are Running and Ready.
kubectl get pods -n <namespace>
Check Pod Events: If Pods are not ready, use kubectl describe pod on them to find the cause.
Test Connectivity from Another Pod:
kubectl exec -it <another-pod-name> -n <namespace> -- /bin/bash
Inside the shell, try curl : or nslookup .
Common Causes & Solutions:

Incorrect Selectors: Service selector does not match Pod labels. Correct labels or selector.
Pods Not Ready: Pods are crashing, failing readiness probes, or not yet started. Debug the Pods first.
Network Policies: Network policies might be blocking traffic between Pods or from the Service to the Pods.
DNS Issues: Service name is not resolving correctly. Check CoreDNS logs and configuration.
Scenario 4: Ingress Not Routing Traffic
Symptom: External traffic directed to your Ingress hostname/path does not reach the application.

Diagnosis Steps:

Describe the Ingress:
kubectl describe ingress <ingress-name> -n <namespace>
Check rules, backend service/port, and annotations.
Check Ingress Controller Logs: Identify your Ingress controller (e.g., Nginx, Traefik) and check its logs.
kubectl logs -n <ingress-controller-namespace> -l app.kubernetes.io/name=<ingress-controller-label>
Look for errors related to your hostname, backend Service, or SSL certificates.
Verify Backend Service and Pods: Ensure the Service and Pods targeted by the Ingress are healthy and accessible (as per Scenario 3).
Check DNS: Confirm that your hostname's DNS record points to the external IP of your Ingress controller.
Common Causes & Solutions:

Incorrect Ingress Rules: Mismatched hostnames, paths, or backend configurations.
Ingress Controller Issues: The controller itself might be unhealthy or misconfigured.
SSL Certificate Problems: If using HTTPS, issues with certificates (expired, incorrect name, missing) will prevent routing.
Network Policies: Network policies might block traffic from the Ingress controller Pods to the application Pods.
Connecting to Monitoring Tools
For all these scenarios, once you've identified the component causing the issue, you might then use tools like Prometheus and Grafana to:

Monitor resource utilization (CPU, memory) of Pods and Nodes.
Track request rates and error rates for Services and Ingress.
Visualize application-specific metrics that might indicate internal problems.
This lesson provides the foundational kubectl skills. The next lesson will build upon this by showing how to leverage monitoring and logging tools to gain even deeper insights.

Lab 1: Debugging a Failing Pod with Logs and Events

In this lab, you will simulate a failing Pod and use kubectl describe and kubectl logs to diagnose the issue. This hands-on exercise will reinforce the concepts learned in the previous sections.

Prerequisites
Minikube or Kind running.
kubectl configured to connect to your cluster.
Basic understanding of Pods and Deployments.
Lab Steps
Create a faulty Deployment: We'll create a Deployment that intentionally has an error. For example, it might try to use an image that does not exist or have a misconfigured command. Save the following YAML as faulty-app-deployment.yaml:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: faulty-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: faulty-app
  template:
    metadata:
      labels:
        app: faulty-app
    spec:
      containers:
      - name: faulty-app-container
        # This image intentionally does not exist or is misconfigured
        image: non-existent-registry/faulty-app:v1.0
        ports:
        - containerPort: 8080
        # Example of a command that might fail if dependencies are missing
        # command: ["python", "app.py"]
        # args: ["--config", "/etc/app/config.yaml"]
Apply the Deployment:
kubectl apply -f faulty-app-deployment.yaml
Observe the Pod Status: Wait a moment and check the status of the Pods created by the Deployment.
kubectl get pods -l app=faulty-app
You will likely see the Pod in a state like ImagePullBackOff, ErrImagePull, or CrashLoopBackOff.

Inspect the Pod with `kubectl describe`: Now, use describe to get more details. Replace  with the actual name of your Pod (e.g., faulty-app-xxxxx-yyyyy).
kubectl describe pod <pod-name> -l app=faulty-app
Carefully examine the output, paying close attention to the Status, Reason, and especially the Events section. What do the events tell you about why the Pod is failing?

Examine Container Logs: Even though the image might not be pulling, or the container is crashing, there might be logs from previous attempts or related processes. Try to fetch the logs.
kubectl logs <pod-name> -l app=faulty-app
If the container is repeatedly crashing, you might need to view logs from the previous instance:

kubectl logs -p <pod-name> -l app=faulty-app
What information do the logs provide? Do they corroborate the events seen in describe?

Identify the Root Cause: Based on the output from describe and logs, what is the primary reason this Pod is failing? (e.g., incorrect image name, missing configuration, etc.)
Fix the Deployment: Edit the faulty-app-deployment.yaml file. Correct the image name to a valid one (e.g., nginx:latest or a simple busybox image like busybox:latest). If you used a command that might fail, comment it out or fix it.
Re-apply the Deployment:
kubectl apply -f faulty-app-deployment.yaml
Verify the Fix: Check the Pod status again.
kubectl get pods -l app=faulty-app
The Pod should now be in a Running state. You can use kubectl describe and kubectl logs again to confirm its healthy status.

Clean Up
Remove the Deployment:

kubectl delete deployment faulty-app
Lab 2: Interactive Container Troubleshooting with `kubectl exec`

This lab focuses on using kubectl exec to interact directly with a container's environment to diagnose issues. We'll simulate a scenario where an application is failing due to a missing configuration file.

Prerequisites
Minikube or Kind running.
kubectl configured.
A running Pod (we'll create one).
Lab Steps
Create a Pod with a Missing Configuration: We'll use a simple Pod that expects a configuration file at a specific path. Save the following YAML as config-test-pod.yaml:
apiVersion: v1
kind: Pod
metadata:
  name: config-test-pod
spec:
  containers:
  - name: main-container
    # Using a simple busybox image for demonstration
    image: busybox:latest
    # Command to try and read a config file, which will fail if it's missing
    command: ["sh", "-c", "echo 'Attempting to read config...' && cat /app/config/settings.conf && echo 'Config read successfully.'"]
    volumeMounts:
    - name: config-volume
      mountPath: /app/config
  volumes:
  - name: config-volume
    emptyDir: {} # An emptyDir volume, we will NOT populate it in this step
Apply the Pod:
kubectl apply -f config-test-pod.yaml
Observe Pod Status and Logs: Check the Pod's status and logs.
kubectl get pods config-test-pod
kubectl logs config-test-pod
You will likely see that the command inside the container failed because /app/config/settings.conf does not exist. The Pod might exit or the command might just print an error and finish.

Use `kubectl exec` to Inspect: Now, let's get inside the container to see the file system and verify the configuration path.
kubectl exec -it config-test-pod -- /bin/sh
Once you have the shell prompt (#), try the following commands:

List the contents of the /app/config directory:
ls -l /app/config/
You will see that the directory is empty, confirming the configuration file is missing.

Check the root directory or other relevant paths to understand the container's file system structure.
Exit the shell:
exit
Simulate Adding the Configuration: We can use kubectl exec again, this time to create a dummy configuration file.
kubectl exec config-test-pod -- sh -c 'echo "DATABASE_URL=postgres://user:pass@host:port/db" > /app/config/settings.conf'
This command executes a shell command inside the container to create the file with some content.

Re-run the Original Command (or observe Pod behavior): If the Pod was designed to restart or re-run its command upon changes, you might see it succeed now. If not, you might need to restart the container or re-apply the Pod definition. For this simple example, let's re-apply the Pod definition to ensure the command runs again with the new file. First, delete the existing Pod:
kubectl delete pod config-test-pod
Then, re-apply the YAML:

kubectl apply -f config-test-pod.yaml
Now, check the logs again:

kubectl logs config-test-pod
You should now see output indicating the configuration file was read successfully.

Clean Up
Remove the Pod:

kubectl delete pod config-test-pod
